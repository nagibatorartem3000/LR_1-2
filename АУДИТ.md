# Технический аудит исходной программы («Росреестр .py», 2939 строк)

## 1. Как устроена исходная программа

Единственный движок — браузерная автоматизация Playwright (persistent context,
профиль `rosreestr_profile`, ручной вход и ручная капча). Весь сбор данных идёт
через экран: заполнение строки поиска → клик «Найти» → опрос страницы каждые
POLL_MS=150 мс → чтение текста списка → клик по строке → ожидание карточки →
разбор текста карточки → закрытие → возврат к списку. Никакие сетевые ответы
сервиса не используются напрямую.

## 2. Найденные проблемы

### 2.1. Скорость: ожидания вместо ответов сервера

| Место | Проблема | Цена |
|---|---|---|
| `wait_for_results` (1438) | опрос страницы 150 мс + `SEARCH_TIMEOUT=30` с; пустая выдача определяется только по тайм-ауту/тексту | каждая пустая выдача съедает 5–30 с |
| `wait_card_open` (1587) | `CARD_CLICK_WAIT=8` с, повторные клики, `CARD_WAIT=30` с | карточка по сети приходит за ~1,5 с (замер по HAR), экранное открытие — 5–8 с |
| `PAUSE_AFTER_TYPING=0.8`, `CARD_CLOSE_PAUSE=0.8`, `PAUSE_NEXT_PAGE=1.0` | фиксированные паузы на каждое действие | на дом из 30 квартир только «служебных» пауз ~40–60 с |
| `with_retry` (1876) | при сбое перезагрузка сайта и `AUTO_RECOVER_WAITS=(5,10,20,30)` даже если сбой был одиночным 5xx | простой до минуты на разовый сбой |

### 2.2. Ошибки сайта, принимаемые за «объекта нет»

- Пустой результат нигде не отличён от ошибки: если сервер вернул 5xx или
  обрезанный HTML, `wait_for_results` просто не находит строк результатов —
  программа делает вывод «выдача пуста». Квартира помечается отсутствующей.
- `check_rate_limit` ловит только текст «слишком много запросов»; отказ 401/403/429
  без такого текста выглядит как пустая выдача.
- В `run_search`/`wait_for_results` нет классификации ответов: временная ошибка,
  капча и «не найдено» неразличимы.

### 2.3. Пропуск квартир

- **Лимит 100 результатов.** Поиск по адресу дома отдаёт максимум 100 строк
  (`RESULTS_CAP`). У домов, где помещений больше 100 (кв + комнаты + нежилые),
  всё, что не влезло, молча теряется; программа не знает, что выдача обрезана.
- **Нестабильность выдачи.** Два одинаковых запроса с интервалом 25 с дают
  пересекающиеся, но разные подмножества (замер: 94 из 100 общих, порядок
  другой). Исходная программа читает список один раз → часть квартир не видна
  вообще, и это не обнаруживается.
- **`EMPTY_STREAK_LIMIT=3`** (2288): после трёх пустых поисков подряд добор
  прекращается — при нумерации с пропусками (1,2,3,7,8…) это гарантированный
  пропуск квартир, особенно когда неизвестно ожидаемое число.
- **Проверка «кв. 31» только с `BIG_PROBE_FROM=20`** и только по одному номеру:
  дом с 31 квартирой, где в списке показали 30, определяется как «ровно 30».

### 2.4. Неправильная проверка адреса

- `match_house` сравнивает токены текста адреса. «Кировская обл» в адресе
  Росреестра даёт «лишний» токен, которого нет в адресе ГИС ЖКХ → квартиры
  **правильного** дома отклонялись (причины отклонения не записывались).
- Корпуса: «д 5к2» и «д 5 к2» дают разные ключи дома → помещения корпуса 2
  отклонялись или приписывались не тому дому.
- Причины отклонения объекта нигде не сохранялись — проверить логику после
  прогона было невозможно.

### 2.5. Потеря прогресса и устаревший кэш

- Excel пишется один раз в конце полного прогона; падение в середине = потеря
  всего (частично смягчено кэшем JSON, но он пишется не атомарно).
- Кэш не имеет версии правил, совместимой с новыми полями: после изменения
  логики старые записи считаются годными, хотя в них нет формы собственности.
- Повторный запуск заново открывает карточки, уже успешно прочитанные
  (`card_ok`), если дом в целом был помечен «с ошибкой».

### 2.6. Избыточные запросы

- Один и тот же адрес ищется заново на каждом этапе (здание → список → добор)
  без переиспользования ответов.
- Уже открытые карточки открываются повторно при любом повторном проходе дома.
- `flag_premises`/`stage_needed` сокращают часть работы, но решение принимается
  по первому списку, который сам может быть неполным.

## 3. Что подтверждено исследованием сервиса (HAR + открытые замеры)

- Поиск по адресу: `GET /account-back/address/search?term=...&objType=all` —
  без капчи, максимум 100 строк, выдача **нестабильна** между вызовами.
- Карточка: `POST /account-back/on` с `{"filterType":"cadastral","cadNumbers":[...]}`;
  в ответе структурированные поля: адрес по полям (street/house/korpus/flat/litera),
  назначение кодом (204001000000 нежилое здание, 204002000000 жилой дом,
  204003000000 МКД, 206001000000 нежилое помещение, 206002000000 жилое
  помещение), `rights[]`, `encumbrances[]`, площадь, этаж, кадастровая
  стоимость, статус. Карточка приходит за ~1,5 с.
- Коды отказов: 406 — нужна капча; 401/403/429 — отказ; 5xx — ошибка сервера;
  200 с JSON-объектом вместо массива — нечитаемый ответ. Ни один из этих
  вариантов не означает «объект не существует»; «не существует» — только
  пустой `elements[]` у карточки или пустой массив у поиска.

## 4. Вывод

Фундаментальная проблема — сбор данных через экран при наличии стабильного
JSON API того же сервиса. Экранный движок медленнее в 3–5 раз, не различает
ошибки и пустую выдачу и теряет квартиры из-за лимита 100 и нестабильности
выдачи. Эти проблемы не исправляются настройкой пауз — требуется смена
источника данных (что и сделано в `rosreestr_optimized.py` при сохранении
экранного движка как резервного).
